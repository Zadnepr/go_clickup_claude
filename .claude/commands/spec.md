Входные данные (каждая ссылка с новой строки):

$ARGUMENTS

Твоя задача — восстановить, что на самом деле требуется сделать, и выдать это
одним проверяемым списком. Код ты не смотришь и не оцениваешь: результат этой
команды — вход для ревью, а не само ревью.

# 0. РАЗБОР ВХОДА

Классифицируй каждую непустую строку:

- **задача ClickUp** — `app.clickup.com/t/...`, кастомный ID (`DEV-42`) или
  нативный ID. Основной вход, обычно единственный.
- **источник ТЗ** — URL Notion, путь к файлу, текст требований. Дополняет задачу.
- **ветка или номер PR** — используется только для отсечки по дате (см. 3.4).

Задач может быть несколько. Тогда на каждую — свой отдельный документ,
не смешивай требования из разных задач.

# 1. СБОР ДАННЫХ

Ссылку передавай в `cup` как есть — он понимает URL, кастомные и нативные ID.

```bash
cup task <id> --json                    # описание, кастомные поля, чек-листы,
                                        # зависимости, связанные задачи, даты
cup comments <id> --json                # комментарии с ID, авторами и датами
cup subtasks <id> --include-closed      # подзадачи
cup attachments <id>                    # вложения: ТЗ часто лежит файлом
```

Треды обязательны: в JSON комментариев смотри счётчик ответов и для каждого
непустого вызывай `cup replies <commentId> --json`. Требования правят
преимущественно в тредах — пропустив их, ты соберёшь ТЗ месячной давности.

Ссылки на Notion, найденные в описании, комментариях, кастомных полях
и вложениях, добавь к источникам ТЗ. Подзадачи разбирай как часть требований
родительской задачи, а не как отдельные документы.

Если `cup` не настроен или задача недоступна — сообщи одной строкой
и работай с тем, что передано вручную. Авторизацию не чини.

# 2. БАЗОВОЕ ТЗ

Базовое ТЗ — исходная постановка до обсуждения. Собери его из:

**Описания задачи ClickUp.** Кастомные поля с критериями приёмки и чек-листы —
тоже часть постановки, их регулярно забывают.

**Notion:**

```bash
notion-cli "<url>"
```

- Длинная страница → `notion-cli "<url>" --file`, затем прочитай файл
  по напечатанному пути. Не вываливай мегабайт Markdown в контекст.
- Комментарии на странице читай — уточнения часто живут только там.
  Отключай (`--no-comments`) только если страница слишком большая.
- Дочерние страницы не раскрываются сами: если дочерняя относится к задаче,
  забери её отдельным вызовом.
- Страница оказалась базой/коллекцией → она не рендерится, запроси прямую ссылку.
- Не настроен, токен протух, нет доступа → сообщи одной строкой и считай
  источник недоступным. Авторизацию не чини.

**Файлы в репозитории и вложения** — прочитай напрямую.

Если базового ТЗ нет вообще, а комментарии есть — собирай требования только
из них и явно это укажи. Если нет ни того, ни другого — скажи об этом и
остановись, не сочиняй постановку.

# 3. ХРОНОЛОГИЯ

## 3.1. Лента

Выстрой все сообщения по возрастанию даты в одну ленту: комментарии верхнего
уровня, ответы в тредах, комментарии на страницах Notion. Для каждого держи
дату, автора и суть.

## 3.2. Классификация

Каждое сообщение отнеси к одному из типов:

- **уточнение** — деталь к существующему требованию;
- **изменение** — требование переформулировано или заменено;
- **отмена** — требование снято, отложено, вынесено в отдельную задачу;
- **добавление** — новое требование, которого не было в постановке;
- **вопрос без ответа** — спросили и не ответили;
- **шум** — статусы, «сделал», «спасибо», сроки, ссылки без контекста.

Дальше работай только с первыми четырьмя.

## 3.3. Правила разбора

- **Позднее сильнее раннего.** При противоречии выигрывает более свежее
  сообщение, но само противоречие фиксируй отдельно — молча перезаписывать
  требование нельзя, это ровно то место, где теряется смысл.
- **Договорённость сильнее реплики.** Предложение, оставшееся без ответа
  и без подтверждения от постановщика, — вопрос без ответа, а не требование.
  Чужое «может, сделаем ещё и так?» не повышается до пункта ТЗ.
- **Роль автора учитывай, но не абсолютизируй.** Слово постановщика или
  ответственного весомее реплики стороннего участника.
- **Устные договорённости не восстанавливай.** Если в комментариях есть
  «обсудили в созвоне, делаем как договорились» — это не требование,
  а открытый вопрос.

## 3.4. Отсечка по дате

Если во входе есть ветка или номер PR, возьми дату последнего коммита.

Рабочая копия — общий корень с несколькими независимыми git-репозиториями
рядом (`panels/`, `sommerce/`, `editor/` и т.д.). Если номер PR передан
полным URL (`https://github.com/<org>/<repo>/pull/<N>` или
`.../<repo>/-/merge_requests/<N>`), репозиторий — это `<repo>` из пути;
перейди в соответствующую подпапку (`cd <repo>`) перед git-командами. Если
передана только ветка или голый номер PR без репозитория в URL — определить
репозиторий нельзя: сообщи об этом одной строкой и работай без отсечки по
дате, не перебирая репозитории наугад.

```bash
git fetch origin
git log -1 --format=%cI <ревизия>
```

Требования, появившиеся позже этой даты, помечай отдельно: они не могут
считаться невыполненными для уже написанного кода.

Ветка не передана → отсечки нет, все требования актуальны.

# 4. ФОРМУЛИРОВКА ТРЕБОВАНИЙ

Требование должно читаться так, чтобы по нему можно было проверить код.
Это главное отличие ТЗ от пересказа обсуждения.

- Одно требование — одна проверяемая мысль. «Экспорт с фильтрами и лимитом» —
  это два пункта.
- Утвердительная формулировка: что должно быть, а не что обсуждали.
- **Конкретику сохраняй дословно**: числа, форматы, названия полей и методов,
  коды ошибок, границы. Обобщение «валидировать входные данные» вместо
  «отклонять даты старше 2020-01-01 с кодом 422» убивает всю пользу.
- Не переписывай своими словами то, что уже сформулировано точно.
- Нефункциональные требования — лимиты, нагрузка, время ответа, сроки
  хранения, права доступа — выноси отдельными пунктами. Их теряют чаще всего.
- Больше 15 требований → сгруппируй подзаголовками по смыслу, нумерация
  при этом сквозная.

# 5. ФОРМАТ РЕЗУЛЬТАТА

```markdown
---
задача: DEV-2760 «Экспорт заказов»
ссылка: https://app.clickup.com/t/9017679539/DEV-2760
сформировано: 2026-09-08
последний_комментарий: 90170112345 от 2026-08-20
отсечка: коммит abc1234 от 2026-08-18
источники:
  - описание задачи ClickUp
  - Notion «Экспорт заказов»
  - 14 комментариев, 6 ответов в тредах
---

# Уточнённое ТЗ: DEV-2760 «Экспорт заказов»

| № | Требование | Статус | Источник |
|---|-----------|--------|----------|
| 1 | CSV-выгрузка заказов по фильтру дат | база | описание |
| 2 | Даты в формате ISO-8601 | изменено 12.08, Петров | коммент |
| 3 | ~~Выгрузка в XLSX~~ | отменено 14.08, Петров | тред к 12.08 |
| 4 | Лимит 50 000 строк на файл | добавлено 15.08, Иванов | коммент |
| 5 | Ретрай при таймауте S3, 3 попытки | добавлено 20.08 — ПОСЛЕ отсечки | коммент |

## Открытые вопросы
- Что делать при превышении лимита: обрезать или бить на файлы? —
  спросил Иванов 15.08, ответа нет.

## Противоречия
- Описание требует XLSX, комментарий от 14.08 его отменяет. Взят комментарий.

## Не вошло
- Обсуждение сроков и статусов (7 комментариев).
- Предложение добавить экспорт в JSON — без подтверждения постановщика,
  вынесено в открытые вопросы.
```

Поле `последний_комментарий` обязательно: по нему `/review` определяет,
не появилось ли новых сообщений после того, как документ был собран.

Раздел «Не вошло» нужен, чтобы было видно, что ты прочитал всё обсуждение,
а не половину. Одна-две строки, без пересказа.

Отменённые требования оставляй зачёркнутыми — ревью проверяет по ним
обратное: не сделана ли лишняя работа.

# 6. СОХРАНЕНИЕ

Выведи документ в чат целиком — этим твоя работа заканчивается. Файл сама
команда не создаёт: сохранение — забота вызывающей стороны, а не этой
сессии.

- В автоматическом пайплайне (сервис `go_claude_agent`) вызывающая сторона
  сама сохраняет этот текст в базу данных и сама кладёт файл
  `specs/<ID задачи>.md`, которым воспользуется `/review` — ей не нужен
  для этого инструмент записи файлов в этой сессии.
- При ручном запуске, если результат нужен именно файлом (например, чтобы
  передать в `/review` третьим аргументом), попроси об этом отдельно — эта
  команда сама файл не пишет.

Если по этой задаче уже видно предыдущую версию ТЗ (в файле или в контексте
разговора) — прежде чем вывести новый документ, покажи, какие пункты
изменились по сравнению с ней: накопленные правки ТЗ полезнее, чем немая
перезапись.

# ОГРАНИЧЕНИЯ
- Не смотри код и не оценивай реализацию — это работа `/review`.
- Не додумывай требования: чего нет ни в постановке, ни в подтверждённых
  комментариях, того нет в ТЗ.
- Не выбрасывай требование только потому, что оно кажется устаревшим.
  Отмена фиксируется, если она была явной.
- Ничего не меняй в ClickUp и Notion: не пиши комментарии, не трогай статусы
  и описания. Только чтение.
- Никогда не выводи и не сохраняй секреты и токены в ответ или файлы.
