# Полное досье по задаче ClickUp

Один вызов `cup task <id>` даёт не всё. Комментарии, подзадачи, вложения, время и участники живут в отдельных командах, а треды ответов — ещё на уровень глубже. Этот скилл описывает, что именно нужно собрать и в каком порядке, чтобы у пользователя на руках оказалась вся картина по задаче, а не её верхушка.

## Предусловия

Работает только там, где можно выполнять shell-команды на машине пользователя (Claude Code, Cowork, терминал). В веб-чате `cup` недоступен.

Проверить, что CLI жив, можно через `cup auth` — но делать это на каждый запрос не нужно. Если первая команда упала с ошибкой конфигурации, тогда и разбирайтесь: чаще всего лечится `cup init` или переменными `CU_API_TOKEN` / `CU_TEAM_ID`.

## Идентификатор задачи

Все команды принимают три формы, конвертировать ничего не надо:

- нативный ID: `abc123`
- кастомный ID с префиксом: `PROJ-123`, `DEV-42`
- полный URL: `https://app.clickup.com/t/9017679539/DEV-2760`

Если пользователь дал ссылку — передавайте ссылку как есть.

## Уровни сбора

Не всегда нужен полный проход. Выбирайте глубину по запросу.

**Уровень 1 — быстрый ответ на конкретный вопрос** («какой статус?», «кто исполнитель?»):

```bash
cup task <id>
```

Без `--json` в пайпе выводится компактный Markdown — этого хватает и это дешевле по контексту.

**Уровень 2 — задача плюс обсуждение** («что там происходит?», «изучи задачу»):

```bash
cup activity <id>
```

`activity` объединяет детали задачи и историю комментариев в одном выводе. Это правильная отправная точка для большинства запросов «расскажи про задачу».

**Уровень 3 — полное досье** («собери всю информацию», «мне надо въехать в задачу перед работой», хендовер). Выполняйте весь блок ниже.

## Полный сбор

Запускайте команды одну за другой. Каждая независима, порядок влияет только на удобство чтения.

```bash
cup task <id> --json          # ядро: описание, статус, приоритет, даты, теги,
                              # кастомные поля, чек-листы, зависимости, связанные задачи
cup subtasks <id> --include-closed   # подзадачи, включая закрытые
cup comments <id>             # все комментарии
cup attachments <id>          # вложения: имя, размер, ссылка, дата
cup task-members <id>         # у кого есть доступ, с ролями
cup time-in-status <id>       # сколько задача провела в каждом статусе
cup time list --task <id> --days 365 --all   # списанное время всей команды
```

Ключевые моменты:

- **`--json` обязателен именно для `cup task`.** В Markdown-виде команда отдаёт структурированную выжимку, а полный набор полей — кастомные поля, чек-листы, вложенные объекты — возвращает только JSON. Остальные команды в Markdown читаются лучше и занимают меньше контекста, `--json` им добавляйте только если нужны точные ID для последующих действий.
- **`cup time list` по умолчанию врёт по двум осям**: показывает только ваши записи и только за 7 дней. Для досье нужны `--all` и `--days`, иначе чужие списания и старая история потеряются.
- **`--include-closed` у подзадач** — без него закрытые подзадачи не видны, а для понимания «что уже сделано» они и есть самое интересное.

### Треды в комментариях

`cup comments` возвращает верхний уровень. Если у комментария есть ответы, они не приедут сами:

```bash
cup comments <id> --json      # взять ID комментариев
cup replies <commentId>       # для каждого комментария с ответами
```

Тянуть `replies` для каждого комментария подряд расточительно. Разумный компромисс: смотреть на счётчик ответов в JSON и запрашивать треды только там, где они непустые. Если обсуждение явно ключевое для запроса пользователя — тяните все.

### Чек-листы

Уже приходят внутри `cup task <id> --json`. Отдельная команда `cup checklist view <id>` нужна, только если требуется читаемый вид или ID элементов для последующего редактирования.

## Экономия запросов

У ClickUp лимит около 100 запросов в минуту (Business). Полное досье — это 7–10 запросов на задачу, плюс по одному на каждый тред. Для одной задачи это неважно. Но если пользователь просит досье на десяток задач:

- начните с `cup task` и `cup comments` по каждой, а остальное добирайте только там, где это реально нужно;
- для больших объёмов существует `cup export` — он складывает задачи с комментариями, подзадачами и вложениями в локальный архив и умеет докачивать инкрементально. Для «выгрузи всё по проекту» это правильный инструмент, а не цикл по `cup task`.

## Формат ответа

Собранные данные не вываливайте сырыми — пользователь просил информацию, а не транскрипт консоли. Сведите в такую структуру, пропуская пустые разделы:

```markdown
## [ID] Название задачи

**Статус** · **Приоритет** · **Исполнители** · **Дедлайн** · **Список / спринт**
Ссылка на задачу

### Суть
Описание задачи, пересказанное своими словами. Если описание длинное —
выжимка плюс дословно все конкретные требования, критерии приёмки и цифры.

### Кастомные поля
Только заполненные, в виде «поле — значение».

### Подзадачи
Список со статусами. Закрытые пометить.

### Чек-листы
Прогресс вида 3/7 и невыполненные пункты.

### Зависимости и связи
Что блокирует, что блокируется, связанные задачи.

### Обсуждение
Хронология по существу: решения, изменения требований, открытые вопросы,
кто что обещал. Треды — вложенно. Болтовню и «+1» опускать.

### Вложения
Имя, что это, ссылка.

### Время
Сколько провисела в каждом статусе, сколько списано и кем.

### Что важно знать
2–4 пункта: неочевидные ограничения, противоречия между описанием
и комментариями, вопросы без ответа, риски.
```

Последний раздел — самый ценный. Именно ради него пользователь просит «всю информацию»: он хочет не архив, а понимание. Расхождение между тем, что написано в описании, и тем, о чём договорились в комментариях, встречается постоянно и стоит того, чтобы вынести его наверх.

Если пользователь спрашивал что-то конкретное — ответ на его вопрос идёт первым, досье следом.

## Чего этот скилл не делает

Скилл читающий. Не меняйте статусы, не пишите комментарии, не редактируйте описание в рамках сбора информации — даже если по содержанию задачи кажется, что «надо бы обновить». Любая запись в ClickUp требует отдельной явной просьбы пользователя.

## Если что-то не сработало

- `No config file found` / `Config missing apiToken` — CLI не настроен: `cup init` или `CU_API_TOKEN`.
- Задача не найдена по кастомному ID — кастомные ID резолвятся через `teamId` из конфига; если рабочих пространств несколько, проверьте профиль: `cup profile list`, `cup profile use <name>` или разовый `-p <name>`.
- Пустой вывод у любой команды — старая версия CLI, обновить: `npm install -g @krodak/clickup-cli`.

Полный справочник по остальным командам `cup` — в базовом скилле CLI (`cup skill`) и в `cup <команда> --help`.
