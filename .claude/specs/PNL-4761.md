# Уточнённое ТЗ: PNL-4761 «User app. Условия для показа Install app баннера»

## Контекст

Install app баннер (PWA-баннер, введённый в PNL-3957) сейчас показывается всем мобильным посетителям Premium-панелей без ограничений по авторизации и платежам. Продакт обнаружил, что часть установивших приложение так и не возвращается — баннер приводит «холодных» визиторов низкого качества. Задача — сузить аудиторию показа до платящих авторизованных юзеров.

## Требования

| № | Требование | Статус | Источник |
|---|-----------|--------|----------|
| 1 | Install app баннер показывается только авторизованным юзерам (на внутренних страницах панели) | база | описание задачи, Notion «Решение» |
| 2 | Install app баннер показывается только при наличии у юзера платежа со статусом Completed | база | описание задачи, Notion «Решение» |
| 3 | Как только у юзера появляется Completed-платёж, баннер показывается на любых внутренних страницах панели (кроме исключений, см. №5) на текущих условиях, пока юзер его не закроет | уточнение, Notion | Notion «Решение» |
| 4 | Показ баннера НЕ связывается с суммой трат юзера — достаточен сам факт Completed-платежа, привязка к порогу трат не нужна | уточнение, Notion | Notion, callout в разделе «Решение» |

## Открытые вопросы

- **Определение «платящего» юзера для баннера vs. для Ticket system.** ТЗ (Notion) обосновывает новую логику ссылкой на «уже существующую логику включения Ticket system», предполагая аналогичный принцип, но не даёт точной формулы. В ревью (Андрей Заднепряный, 26.08) зафиксировано расхождение: старое условие `isEnabledTicketSystem()` — `mode = MANUAL` (безусловно) ИЛИ (`mode = AUTO` И `type <> FREE`); новая логика для баннера игнорирует `mode` и режет по `type NOT IN (FREE)` + `panel_payment_method_id NOT IN (PANEL_METHOD_FREE)`. Из-за этого юзеры с ручным платежом типа Free или auto-платежом с `panel_payment_method_id = -2` теряют доступ к тикетам на панелях с `TICKET_SYSTEM_ENABLE_FOR_PAYING_USERS`. Явного ответа продакта в треде нет — нужно либо согласовать единую формулу «платящего юзера», либо явно развести понятия для баннера и для тикетов.
- **METHOD_BONUS как «Completed платёж».** Не уточнено в ТЗ, должен ли вручную начисленный бонус (админ выбрал метод Free/Bonus при ручном пополнении) засчитываться как «Completed платёж», дающий право на показ баннера. В ревью поднят вопрос — явного ответа продакта в треде нет.
- **Расхождение с метрикой New Paying Users.** В отчётах (`BaseReportQuery.php`, метрика New Paying Users — та самая, на данных которой построено обоснование в ТЗ) «платящий юзер» считается по старой формуле (`mode = MANUAL` ИЛИ `mode = AUTO` И `type <> FREE`). Если баннер/тикеты после этой задачи считают иначе, возникает два разных определения «платящего юзера» в проекте. Явного решения (унифицировать или сознательно разойтись) в треде нет.
- **Demo-панели.** ТЗ не упоминает демо-панели явно. У `isEnabledTicketSystem()` есть guard на demo-режим, но параллели для баннера в обсуждении не зафиксировано — открыт вопрос, должен ли баннер вести себя как-то по-особому на демо-панели.
- **Исключение страницы `pwa-payment-complete` (страница успешной оплаты).** В ревью отмечено, что помимо страниц Add funds (единственное исключение по ТЗ) из показа исключена ещё и страница успешного завершения PWA-платежа. Разработчик (Григорий Ляпин, 02.09) обосновал это трактовкой пункта ТЗ «не показываем баннер на странице оплаты, это тоже страница оплаты» — но это интерпретация разработчика, явного согласования с постановщиком (Шеметов Лев) в треде нет. Формально это момент, когда юзер как раз становится «платящим» — то есть кандидатом на показ баннера, что противоречит духу расширения исключения.

## Противоречия

- Между Notion-ТЗ (обоснование через «аналогичную» логику Ticket system) и фактическим поведением, зафиксированным в ревью (новая логика для баннера не совпадает с логикой Ticket system и меняет её поведение, хотя ТЗ про изменение Ticket system ничего не говорит) — расхождение не разрешено явно в треде задачи.
