# Уточнённое ТЗ: PNL-4866 «Public order: проработать UX для всех кейсов и сценариев оплаты»

## Контекст (из описания задачи)

Для заказа без регистрации (Public order) сейчас описан и реализован только happy path сценария оплаты (см. справочный документ «Заказ без регистрации»). Задача — предоставить понятный UX для всех основных исходов оплаты, чтобы пользователю было ясно, что произошло с его платежом или заказом, даже если что-то пошло не так.

Общий флоу (база, из документа «Public order: UX...»):
1. На странице `/order` отображается выбор платёжных методов.
2. Все проверки (Transaction ID, доп. поля) выполняются на форме.
3. После валидации формы — редирект на статусную страницу.
4. Дальнейшее поведение зависит от конкретного сценария оплаты (см. ниже).

**Важно:** 08.09.2026 разработчик (Andrey Globin) сообщил об изменении этого флоу для платёжек с чекаут-страницей — см. п. 6.

## Требования

| № | Требование | Статус | Источник |
|---|-----------|--------|----------|
| 1 | Для каждого Draft Order, созданного после нажатия пользователем кнопки Pay, генерируется статусная страница | база | Notion «Public order: UX...» |
| 2 | Платёж в статусе **Pending** → статусная страница показывает статус ожидания платежа, вместо Order ID текст: «Waiting for payment» | база | Notion «Public order: UX...» |
| 3 | Платёж **Completed**, заказ ещё не создан → статусная страница, вместо Order ID текст: «Your order is being processed» (согласно текущей логике happy path) | база | Notion «Public order: UX...» |
| 4 | Платёж Completed, заказ создан → статусная страница показывает все данные заказа (согласно текущей логике) | база | Notion «Public order: UX...» |
| 5 | Платёж **Expired**, Draft Order удалён → статусная страница (по хешу) удаляется | база | Notion «Public order: UX...» |

**Примечание по пп. 13–15:** формулировка разработчика лаконична («Поменяли флоу / чекаут полностью остается в форме / на статусной странице просто запукается отрисовка отдельных груп платежек (qr и виджеты)») и не детализирует, как это соотносится с пп. 16–20 (описанными в базовом документе как сценарии для *внешней* чекаут-страницы). Изменение принято как есть, без додумывания деталей реализации — см. «Открытые вопросы».

### Сценарий 3: платёжка не настроена

| № | Требование | Статус | Источник |
|---|-----------|--------|----------|
| 27 | Проверка настроенности платёжки выполняется до попытки пользователя начать оплату | база | Notion «Public order: UX...» |
| 28 | Если платёжка не настроена — редирект пользователя на статусную страницу, соответствующую Draft Order (без возможности вернуться и выбрать другой метод оплаты — сознательное решение, см. уточнение ниже) | база, уточнено 28.08.2026 (Ekaterina Gusakova) | Notion (тред) + комментарий |
| 29 | При этом создаётся запись в таблице payments админа и Draft Order (аналогично текущей логике для платежей add funds) | база | Notion «Public order: UX...» |

**Уточнение к п. 28** (тред в Notion, разрешён): на вопрос «зачем редиректить на статусную, если со статусной нельзя вернуться и выбрать другой платёжный метод» продакт-менеджер (Ekaterina Gusakova, 28.08.2026) ответила: «У нас нет состояния "платёжка не настроена". Мы делаем единую логику с переходом на статусную, и если форма провалидирована, то система кинет на статусную» — то есть отдельного пользовательского состояния «платёжка не настроена» нет, действует общая логика: валидная форма → редирект на статусную.

## Открытые вопросы

- Есть ли ограничения, которые не позволяют при отмене платежа возвращать пользователя именно на предыдущую (а не любую иную) страницу? Как в этом случае должна вести себя Google Analytics? — вопрос поднят Ekaterina Gusakova 24.08.2026, ответа в переписке нет.
- Должна ли статусная страница обновляться через сокеты вместо периодического опроса (polling), описанного в пп. 6–12? Ekaterina Gusakova 24.08.2026 предложила изучить эту возможность («надо узнать, насколько это сложно»); Kirill Bukin 24.08.2026 ответил «обсудили, можно на ревью» — то есть решение принято устно на созвоне и не зафиксировано текстом. Согласно правилам сборки ТЗ устные договорённости не восстанавливаются, поэтому вопрос остаётся открытым, а требования пп. 6–12 (polling) считаются актуальными как есть.
- Нужен ли лоадер/индикатор на статусной странице, дающий понять пользователю, что страница может сама обновиться? — предложение Dmitry Sazhin, 27.08.2026, ответа/подтверждения продакта нет.
- Что именно имел в виду Kirill Bukin вопросом «?» к пункту про интервал опроса «первые 60 сек после успешной оплаты» (28.08.2026)? — вопрос без ответа, суть неясна из контекста.
- Как именно новый флоу «чекаут остаётся в форме» (п. 14) соотносится с пп. 16–20 (сценарии для оплаты через внешнюю чекаут-страницу — успех/отмена/таймаут/техническая ошибка)? Требуют ли эти сценарии переформулировки под новый флоу, или относятся только к платёжкам, которые по-прежнему уводят на внешнюю чекаут-страницу? В переписке это не уточнено.

## Противоречия

Явных противоречий между разными редакциями требований не обнаружено. Формулировка п. 28 в базовом документе изначально могла читаться как открытый вопрос (Dmitry Sazhin усомнился в её целесообразности), но продакт-менеджер подтвердила исходную логику — это уточнение, а не смена решения.

Из него в ТЗ не включены требования, не связанные напрямую с UX разных исходов оплаты.
