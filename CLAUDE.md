# go_claude_agent (сервис `reviewer`)

Этот файл — памятка для Claude Code при работе именно с этим сервисом.
Архитектура, эндпоинты и переменные окружения подробно описаны в
[README.md](README.md) — здесь только то, что обязательно знать *перед*
тем, как что-то менять, и что обычно не очевидно из чтения кода.

## Что это

Go-микросервис, который следит за доской ClickUp и прогоняет задачи через
`claude -p` по двум этапам — сбор уточнённого ТЗ и код-ревью. Сам сервис не
понимает ни код, ни ТЗ: всю содержательную работу делает Claude Code внутри
целевого репозитория через slash-команды.

## Четыре команды, не две

В `.claude/commands/` целевого репозитория лежат **четыре** команды, попарно:

| Команда | Кто вызывает | Что делает |
|---|---|---|
| `/spec-go` | этот сервис (`RunSpec`) | выводит собранное ТЗ только в чат — файл не пишет, писать `.claude/`-инструментом Write запрещено (см. ниже) |
| `/review-go` | этот сервис (`RunReview`) | в ответе только блоки замечаний + машинная строка `ИТОГ: ...` в конце — никакого плана, ТЗ-таблицы или рассуждений в выводе |
| `/spec` | человек, вручную из терминала | то же самое ТЗ, но сама сохраняет файл (`specs/<ID>.md`) и печатает подсказку для запуска `/review` |
| `/review` | человек, вручную из терминала | то же ревью, но с таблицей ТЗ в каждом блоке для контекста и без строки `ИТОГ:` — читает человек, парсить нечем |

Это осознанное разделение, а не дублирование: `-go`-версии оптимизированы
под безголовый (`claude -p`, без диалога) автоматический прогон и минимальный
паразитный текст в комментарии ClickUp; версии без суффикса — под
интерактивную сессию человека в репозитории.

**Меняя логику ревью/сбора ТЗ (например, как искать PR в комментариях),
правь оба варианта параллельно**, если изменение не специфично для
автоматизации/ручного режима. Разошедшиеся команды — источник трудноуловимых
расхождений в поведении.

Сервис проверяет при старте каждого прогона наличие именно `spec-go.md` и
`review-go.md` (`internal/queue/worker.go:requiredCommands`) — это и есть
единственный источник истины насчёт того, какие команды реально вызываются
(см. `Runner.RunSpec`/`RunReview` в `internal/review/runner.go`, буквально
`"/spec-go\n"` и `"/review-go\n"`).

## Где физически лежат команды

`docker-compose.yml` монтирует `../:/repo` — то есть корень `app/`
(родитель этого репозитория), а не сам `go_claude_agent/`. Значит:

- **Живая копия** — `app/.claude/commands/*.md`. Правки туда подхватываются
  сразу, без пересборки и рестарта контейнера (bind mount).
- **Зеркало в этом репозитории** (`go_claude_agent/.claude/commands/*.md`)
  — не используется в рантайме вообще. Оно существует только затем, что
  `app/` сам не под git, а `go_claude_agent/` — под git: так изменения в
  промптах хоть где-то версионируются.

**После правки живой копии — обязательно скопируй её же в зеркало** этого
репозитория (`cp app/.claude/commands/*.md go_claude_agent/.claude/commands/`),
иначе история версий тут же расходится с тем, что реально исполняется.

## Write не разрешён внутрь `.claude/`

Claude Code блокирует запись тулом `Write` в любой путь под `.claude/`
независимо от `--allowedTools` — проверено эмпирически (широкое разрешение
и точечный паттерн `Write(.claude/specs/**)` не помогают). Поэтому:

- `specs/<ID>.md` (файл ТЗ) лежит в корне `REPO_PATH`, НЕ в `.claude/specs/`.
- Ручная `/spec` (allowed-tools включает `Write`) тоже пишет в `specs/`, не
  в `.claude/specs/` — несмотря на то, что более раннее решение (см. git-
  историю `spec.md`) писало именно туда.
- `/spec-go`/`/review-go` вообще не просят `Write` в `--allowedTools`
  (`internal/review/runner.go:run`) — файл `specs/<ID>.md` для них пишет
  сам Go через `os.WriteFile` (`ensureSpecFile` в `worker.go`), из
  содержимого, уже сохранённого в БД (источник истины — не файл, а
  `run_stages`, см. README «Поэтапное выполнение, ТЗ и лог токенов в БД»).

## Рестарт vs пересборка

- Правка `.claude/commands/*.md` в живой копии (`app/.claude/commands/`)
  — эффект мгновенный, рестарт/ребилд не нужен.
- Правка кода в `internal/`, `cmd/` — **нужен ребилд образа**:
  ```bash
  docker compose up -d --build reviewer
  ```
  Простой `restart` без `--build` продолжит гонять старый бинарник.

## Проверка перед тем, как считать изменение готовым

```bash
go build ./... && go test ./...
```

Если менялась логика вокруг `/spec-go`/`/review-go` (промпты, парсинг
вердикта, eligibility) — стоит и живьём прогнать конкретную задачу через
`POST /api/run` (см. README, раздел `POST /api/run`) и посмотреть
`run_stages`/`claude_invocations` в БД (`data/state.db` внутри тома, путь
из `DB_PATH`) вместо того, чтобы верить только юнит-тестам: промпт — это
не код, тестами он не покрыт, а мелкая формулировка легко меняет поведение
модели.

## Прочие грабли этого репозитория

- **`$status` в zsh — read-only переменная** (аналог `$?`). Скрипты
  мониторинга/ожидания результата прогона, использующие переменную с этим
  именем, падают с `read-only variable: status` — называй иначе
  (например `run_status`).
- **`docker-compose.yml`: `env_file:` vs голый `environment: - VAR`.**
  Второе даёт переменным хоста приоритет над `.env` — если правишь `.env`
  и изменение не подхватывается, проверь, не объявлена ли эта же переменная
  голой строкой в `environment:`.
- Рабочая копия внутри контейнера (`REPO_PATH`/`/repo`) — это общий корень
  с несколькими независимыми git-репозиториями рядом (`panels/`,
  `sommerce/`, `editor/` и т.д.), а не один репозиторий. `/spec-go` и
  `/review-go` сами определяют, какой репозиторий относится к задаче, по
  URL PR/MR — Go в это не вмешивается (см. `GitFetch`).
