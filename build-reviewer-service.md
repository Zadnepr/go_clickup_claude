# Задание: микросервис автоматического ревью задач ClickUp

Собери Go-микросервис в Docker-контейнере, который следит за доской ClickUp,
запускает код-ревью силами Claude Code и возвращает результат в задачу и Slack.

Работай итеративно: сначала структура проекта и конфигурация, затем клиент
ClickUp, затем очередь и запуск ревью, в конце Slack и Docker. После каждого
этапа проверяй, что проект собирается.

---

## Главная граница ответственности

Go-сервис — это сантехника. Он не анализирует код, не читает ТЗ, не формулирует
замечания. Вся содержательная работа выполняется процессом `claude -p`, которому
передаётся только ссылка на задачу.

**Go делает:** ловит событие, проверяет условие, дедуплицирует, ставит в очередь,
запускает процесс, забирает вывод, обновляет задачу, шлёт в Slack, логирует.

**Go не делает:** не собирает промпты конкатенацией, не подставляет в них
описание задачи или диф, не разбирает текст ревью регулярками (кроме одной
служебной строки, см. «Контракт вердикта»), не содержит ни слова про PHP,
требования или качество кода.

Если при реализации возникает соблазн добавить в Go логику «а вот здесь надо
понять, что…» — это признак, что задача решается не на том уровне. Такая логика
принадлежит markdown-командам, а не сервису.

---

## Стек и ограничения

- Go 1.23+, стандартная библиотека по максимуму. Веб-фреймворк не нужен:
  хватит `net/http` с `ServeMux`.
- Хранилище состояния — SQLite через `modernc.org/sqlite` (чистый Go, без cgo,
  иначе получишь проблемы со статической сборкой под alpine).
- Логи структурированные, `log/slog`, JSON-хендлер.
- Внешних зависимостей минимум. Для Slack и ClickUp пиши тонкие клиенты сам,
  SDK не тяни.
- Конфигурация только из переменных окружения. Никаких файлов настроек.

## Конфигурация

Все параметры читаются из окружения при старте. Отсутствие обязательной
переменной — падение на старте с внятным сообщением, а не паника при первом
запросе.

| Переменная | Обяз. | Назначение |
|---|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | да | Токен Claude Code, пробрасывается в процесс `claude` |
| `CU_API_TOKEN` | да | Personal API token ClickUp (`pk_...`) |
| `CU_TEAM_ID` | да | ID рабочего пространства |
| `CU_LIST_ID` | да | ID списка отслеживаемой доски |
| `CU_WEBHOOK_SECRET` | да* | Секрет для проверки подписи вебхука |
| `SLACK_WEBHOOK_URL` | да | Incoming webhook канала |
| `REPO_PATH` | да | Путь к рабочей копии репозитория внутри контейнера |
| `REPO_URL` | нет | Если задан — сервис клонирует репозиторий при старте |
| `TRIGGER_TAG` | нет | Тег-триггер, по умолчанию `ai` |
| `STATUS_TRIGGER` | нет | Колонка-триггер, по умолчанию `to check` |
| `STATUS_RUNNING` | нет | Колонка на время проверки, по умолчанию `checking` |
| `STATUS_PASS` | нет | Колонка при отсутствии критичных замечаний |
| `STATUS_FAIL` | нет | Колонка при наличии критичных замечаний |
| `ASSIGNEE_ON_FAIL` | нет | ID пользователя, назначаемого при провале |
| `ASSIGNEE_ON_PASS` | нет | ID пользователя, назначаемого при успехе |
| `WORKER_CONCURRENCY` | нет | По умолчанию 1 |
| `REVIEW_TIMEOUT` | нет | По умолчанию `15m` |
| `RECONCILE_INTERVAL` | нет | По умолчанию `5m`, `0` отключает |
| `PORT` | нет | По умолчанию 8080 |
| `DB_PATH` | нет | По умолчанию `/data/state.db` |

Значения статусов сравниваются без учёта регистра и лишних пробелов: в ClickUp
названия колонок люди правят чаще, чем кажется.

## Требование 1. Получение задач

Два независимых источника событий, оба ведут в одну функцию постановки в очередь.

### 1.1. Вебхук (основной путь)

`POST /webhook/clickup` принимает события ClickUp.

**Проверка подписи обязательна.** ClickUp подписывает каждый запрос: в заголовке
`X-Signature` лежит HMAC-SHA256 от тела запроса в hex, посчитанный секретом,
который выдаётся при создании вебхука. Считай хеш от **сырых байт тела**
до любого парсинга JSON — это главное место, где такие проверки ломаются.
Сравнивай через `hmac.Equal`, не через `==`. Подпись не сошлась — 401 и в лог,
без обработки.

**Отвечай 200 немедленно.** Прочитал тело, проверил подпись, положил в очередь,
вернул 200. Вся работа — в фоне. Причина: ClickUp следит за здоровьем вебхука,
ответ 410 приводит к мгновенной приостановке, любая другая ошибка увеличивает
счётчик неудач, и на сотне вебхук отключается совсем. Уведомления при этом
не приходят, а пропущенные события не досылаются. Таймаут из-за долгой
обработки в хендлере накопит этот счётчик незаметно.

**Подписывайся на несколько событий.** Из пейлоада нужен только `task_id`.
Условие «нужный тег и нужная колонка» проверяется отдельным запросом к API,
потому что тегов в теле события нет. События: `taskStatusUpdated`,
`taskTagUpdated`, `taskCreated`, `taskMoved`. Задачу могут перетащить в колонку,
когда тег уже висит, а могут повесить тег на задачу, которая в колонке давно —
поэтому на каждое событие условие перепроверяется целиком.

Добавь команду `--register-webhook`, которая создаёт вебхук через API,
печатает выданный секрет и завершает работу. Секрет пользователь сам положит
в `.env`.

### 1.2. Сверка (страховка)

Раз в `RECONCILE_INTERVAL` запрашивай задачи списка с фильтром по тегу
и статусу и ставь в очередь всё, чего ещё не обрабатывал. Это нужно, потому
что вебхуки теряются: сервис лежал во время деплоя, ClickUp приостановил
доставку, событие не пришло. Сверка стоит один запрос в пять минут и закрывает
весь этот класс проблем.

При `RECONCILE_INTERVAL=0` сервис работает только на вебхуках. При отсутствии
`CU_WEBHOOK_SECRET` — только на сверке, эндпоинт вебхука не поднимается.
Оба режима одновременно безопасны: дедупликация их развяжет.

## Требование 2. Определение задачи к проверке

Задача берётся в работу, если одновременно:

- среди тегов есть `TRIGGER_TAG`;
- текущий статус равен `STATUS_TRIGGER`;
- задача принадлежит `CU_LIST_ID`;
- по ней нет успешного или выполняющегося прогона в базе.

Условие проверяется **после** получения полной карточки задачи через
`GET /api/v2/task/{id}`, а не по данным события.

Условие не выполнено — не ошибка. Тихо пропускаем и, что важно, **не оставляем
дедуп-запись**: задача должна иметь возможность сработать позже, когда тег
или колонка изменятся.

---

## Требование 3. Перемещение по колонкам

Три перехода:

1. Задача взята в работу → `STATUS_RUNNING`. Делается сразу при снятии
   с очереди, до запуска ревью. Это даёт человеку видимый признак, что процесс
   идёт, и попутно выводит задачу из-под условия триггера.
2. Ревью прошло, критичных замечаний нет → `STATUS_PASS`.
3. Есть критичные замечания или ревью не смогло выполниться → `STATUS_FAIL`.

Если соответствующая переменная не задана, переход не выполняется.

Обработай отказ API на смене статуса: несуществующее имя колонки — частая
ошибка конфигурации. Логируй с указанием того, что пытался поставить, и списка
доступных статусов из карточки задачи.

---

## Требование 4. Назначение исполнителей

Через `PUT /api/v2/task/{id}` полем `assignees` с подполями `add` и `rem`.

- При провале назначается `ASSIGNEE_ON_FAIL`, если задан; иначе — автор задачи
  (`creator.id` из карточки).
- При успехе назначается `ASSIGNEE_ON_PASS`, если задан; иначе состав
  исполнителей не трогается.
- Существующих исполнителей не удаляй, только добавляй. Снятие людей с задачи
  автоматикой почти всегда воспринимается как поломка.

## Требование 5. Запуск /spec и /review

Ядро сервиса. Два последовательных вызова процесса `claude`.

### 5.1. Отдельная сессия на каждую проверку

Каждый запуск `claude -p` — новая независимая сессия. Флаги продолжения
(`--continue`, `--resume`) не используй ни при каких обстоятельствах: контекст
предыдущей задачи, протекший в новую, — это ложные замечания и путаница
в требованиях.

`/spec` и `/review` — тоже две отдельные сессии. Связь между ними идёт через
файл со спецификацией, а не через общий контекст.

### 5.2. Последовательность

```
1. claude -p "/spec\n<url задачи>\n<ветка, если известна>"
   → пишет .claude/specs/<ID>.md в репозитории
2. claude -p "/review\n<ветка или PR>\n.claude/specs/<ID>.md"
   → печатает ревью в stdout
```

Если шаг 1 не создал файл — не прерывайся, запускай `/review` с одной ссылкой
на задачу: команда умеет собирать ТЗ сама. В лог — предупреждение.

Ветка определяется командой `/review` самостоятельно из содержимого задачи.
Не пытайся вытащить её в Go — это ровно та логика, которая должна жить
в markdown.

### 5.3. Запуск процесса

```go
cmd := exec.CommandContext(ctx, "claude", "-p", prompt,
    "--output-format", "json",
    "--allowedTools", "Bash(git:*)", "Bash(cup:*)", "Read", "Grep", "Glob")
cmd.Dir = cfg.RepoPath
cmd.Env = append(os.Environ(), "HOME="+cfg.Home)
```

Критичные детали:

- **`cmd.Env` строй от `os.Environ()`.** Присваивание среза заменяет окружение
  целиком, а не дополняет его; при затирании `claude` не увидит
  `CLAUDE_CODE_OAUTH_TOKEN` и упадёт на авторизации.
- **`HOME` задавай явно.** `claude` пишет состояние в `~/.claude`; в контейнере
  с непривилегированным пользователем переменная бывает пустой.
- **Таймаут через `CommandContext`.** Без него один залипший прогон на большом
  дифе останавливает всю очередь.
- **`--output-format json`** даёт структурированный результат с текстом
  и идентификатором сессии. Проверь точную форму вывода через `claude -p --help`
  на этапе реализации и распарси её типизированно; идентификатор сессии
  положи в базу и в лог, чтобы прогон можно было открыть и посмотреть глазами.
- **Перед каждым ревью — `git fetch --prune origin`** в `REPO_PATH`. Иначе
  проверяться будет вчерашнее состояние веток.
- **stderr захватывай отдельно** и клади в базу при ошибке. Диагностировать
  провалившийся прогон по одному коду возврата невозможно.

## Контракт вердикта

Go должен понять, есть ли критичные замечания, не читая текст ревью.

Для этого в конец команды `/review` добавляется требование печатать последней
строкой:

```
ИТОГ: критичных=<N> важных=<N> минор=<N> статус=<pass|fail|blocked>
```

`blocked` — ревью не смогло выполниться: не нашлась ветка, недоступно ТЗ,
не получен диф. Это не то же самое, что «замечаний нет», и в `STATUS_PASS`
такая задача уходить не должна.

Go берёт **последнее** вхождение строки, начинающейся с `ИТОГ: `. Строки нет
или она не разбирается — считай прогон `blocked` и приложи это к сообщению
в Slack: молча ронять результат нельзя.

Подготовь патч для `review.md` с этим требованием — его пользователь применит
к своей команде. Сам файл не переписывай.

## Требование 6. Комментарий в задаче

Полный текст ревью публикуется комментарием через
`POST /api/v2/task/{id}/comment`.

- Не добавляй свою обвязку вроде «Автоматическая проверка завершена, результат
  ниже» — текст ревью самодостаточен. Уместна одна короткая строка со ссылкой
  на сессию.
- Комментарии в ClickUp имеют ограничение по длине. Если текст не влезает,
  режь по границам разделов и публикуй несколькими комментариями подряд,
  сохраняя порядок.
- `notify_all` не включай.

---

## Требование 7. Уведомление в Slack

`POST` на `SLACK_WEBHOOK_URL` после завершения обработки задачи.

Сообщение содержит: название и ссылку на задачу, вердикт, количество замечаний
по уровням, из какой колонки в какую перемещена, кто назначен, ссылку на сессию.
Формат — Block Kit, критичный вердикт визуально отличим от успешного.

Отдельное сообщение при `blocked` и при внутренней ошибке сервиса: молчаливый
отказ хуже ложного срабатывания, потому что о нём никто не узнает.

Недоступность Slack не должна ронять обработку: логируй и продолжай. Комментарий
и статус в ClickUp важнее уведомления.

## Надёжность

**Дедупликация.** Таблица `runs`: `task_id`, `status` (queued/running/done/failed),
`verdict`, `session_id`, `started_at`, `finished_at`, `error`. Задача ставится
в очередь, только если по ней нет записи в состоянии `queued`, `running` или
`done`. При падении прогона запись переводится в `failed` и **перестаёт**
блокировать повторную постановку — иначе одна ошибка навсегда выкинет задачу
из обработки.

**Восстановление после рестарта.** При старте все записи в состоянии `running`
переводятся в `failed` с пометкой о рестарте. Контейнер перезапустился
посреди ревью — задача должна пройти заново, а не зависнуть.

**Очередь.** Буферизованный канал плюс `WORKER_CONCURRENCY` воркеров. При
переполнении буфера событие не теряется: сверка подберёт задачу позже.

**Лимиты ClickUp.** Около 100 запросов в минуту. Один прогон делает несколько
запросов из Go плюс неизвестное количество из сессии Claude. Поставь лимитер
на клиент ClickUp в Go и обрабатывай 429 с экспоненциальной задержкой.

**Graceful shutdown.** По SIGTERM перестань принимать вебхуки, дай текущим
прогонам завершиться в пределах таймаута, закрой базу.

**Эндпоинты состояния.** `GET /healthz` — процесс жив. `GET /readyz` — база
открыта, репозиторий на месте, `claude --version` отвечает. Проверка `claude`
на старте ловит протухший токен сразу, а не через сутки молчания.

## Docker

Многостадийная сборка.

Стадия сборки: `golang:1.23`, статический бинарник с `CGO_ENABLED=0`.

Финальный образ: базовый с Node.js 22+ (нужен и `claude`, и `cup`), плюс `git`
и `ca-certificates`. Устанавливаются глобально `@anthropic-ai/claude-code`
и `@krodak/clickup-cli`.

Требования к образу:

- Непривилегированный пользователь, `HOME` задан явно через `ENV HOME=...`,
  каталог доступен на запись.
- **Ни одного секрета в `ENV` или `ARG`.** Значения остаются в слоях образа
  навсегда: удаление строки и пересборка их не убирают, а запушенный образ
  означает утёкший токен.
- Том для `DB_PATH` и для `REPO_PATH`.
- `HEALTHCHECK` на `/healthz`.

`docker-compose.yml`: имена переменных перечислены без значений, чтобы
подтягивались из `.env`. Приложи `.env.example` со всеми ключами и пустыми
значениями и `.gitignore`, где `.env` уже указан.

В README — раздел про получение `CLAUDE_CODE_OAUTH_TOKEN` командой
`claude setup-token`, выполняемой на машине с браузером, и предупреждение,
что он расходует подписку, а `ANTHROPIC_API_KEY` тарифицируется отдельно
и одновременно задавать обе переменные нельзя.

Репозиторий внутри контейнера: если задан `REPO_URL`, клонируется при старте;
доступ по deploy key, смонтированному как секрет. Иначе рабочая копия
монтируется томом с хоста.

## Тесты

Обязательно покрой:

- проверку подписи вебхука, включая случай изменённого тела;
- разбор строки `ИТОГ:`, включая отсутствующую и битую;
- дедупликацию: повторное событие по той же задаче не порождает второй прогон;
- возврат в очередь после `failed`;
- логику вычисления целевого статуса и исполнителя от вердикта.

Клиент ClickUp тестируется против `httptest.Server`, реальные вызовы в тестах
не делаются.

## Чего делать не надо

- Не реализуй в Go разбор требований, поиск ветки, чтение ТЗ или анализ
  комментариев задачи. Это делают `/spec` и `/review`.
- Не встраивай текст промптов в Go-код: команды живут в репозитории,
  в `.claude/commands/`, и меняются без пересборки образа.
- Не используй Claude API напрямую и не пиши собственный агентский цикл —
  агент уже есть, это `claude -p`.
- Не снимай исполнителей и не удаляй комментарии.
- Не добавляй веб-интерфейс, метрики Prometheus, авторизацию — вне объёма.

## Готовность

Проект считается готовым, когда:

1. `docker compose up` поднимает сервис, `readyz` отвечает 200.
2. `--register-webhook` создаёт вебхук и печатает секрет.
3. Задача с тегом `ai`, переведённая в `to check`, в течение минуты уходит
   в `checking`, затем получает комментарий с ревью, оказывается в целевой
   колонке, обретает исполнителя, а в Slack приходит уведомление.
4. Повторное событие по той же задаче не порождает второго прогона.
5. Перезапуск контейнера посреди прогона приводит к повторной обработке,
   а не к зависшей задаче.
6. `go test ./...` проходит.
