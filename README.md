# reviewer

Go-микросервис автоматического ревью задач ClickUp: следит за доской,
запускает код-ревью силами `claude -p` и возвращает результат в задачу
ClickUp и в Slack.

Сервис — сантехника. Он не анализирует код, не читает ТЗ и не формулирует
замечания: вся содержательная работа выполняется командами `/spec` и
`/review` внутри `claude -p`, которые живут в целевом репозитории
(`.claude/commands/`) и меняются без пересборки образа.

## Как это работает

1. ClickUp присылает вебхук (или сервис сам сверяется раз в
   `RECONCILE_INTERVAL`, либо запускается вручную через `POST /api/run`) —
   событие ведёт к проверке карточки задачи. Если подходящих задач нет,
   сверка пишет об этом в лог, ничего не делая.
2. Если у задачи есть тег `TRIGGER_TAG`, она в колонке `STATUS_TRIGGER` и по
   ней ещё нет активного прогона — задача берётся в работу.
3. Задача переводится в `STATUS_RUNNING`, текущие исполнители снимаются на
   время проверки (запоминаются, чтобы вернуть их при провале), в Slack и в
   лог уходит сообщение «проверка начата». Дальше сервис проверяет, что в
   репозитории есть команды `.claude/commands/spec.md` и `review.md` — если
   их нет, прогон сразу помечается ошибкой без запуска `claude`.
4. Репозиторий обновляется (`git fetch --prune origin`), запускаются две
   отдельные сессии `claude -p`: сперва `/spec`, затем `/review`.
5. `/review` печатает полный текст ревью и обязан завершить вывод строкой
   `ИТОГ: критичных=N важных=N минор=N статус=pass|fail|blocked` — см.
   [review-patch.md](review-patch.md) для патча, добавляющего это требование
   в вашу команду `/review`.
6. Полный текст ревью публикуется комментарием в задаче. По вердикту:
   - **pass** → колонка `STATUS_PASS`, исполнитель `ASSIGNEE_ON_PASS` (если
     задан) — обычно это финальный ревьюер-человек;
   - **fail или blocked** → колонка `STATUS_FAIL`, исполнитель — первое
     непустое по приоритету:
     1. custom field **Developer** задачи (тип "users" в ClickUp) — это
        реальный разработчик, а не тот, кто был назначен на задачу до
        снятия исполнителей на шаге 3 (им мог быть, например, QA);
     2. `ASSIGNEE_ON_FAIL`;
     3. автор задачи.
     `ASSIGNEE_ON_PASS` в этой цепочке намеренно не участвует: это роль
     проверяющего/ревьюера, а не разработчика — иначе после fail на задаче
     так и оставался бы исполнитель с прошлого pass-прогона, хотя он не
     может её исправить. Снятые на шаге 3 исходные исполнители автоматически
     не восстанавливаются — если ни поле, ни `ASSIGNEE_ON_FAIL`, ни автор
     не годятся, задача останется без исполнителя.
7. Тег `TRIGGER_TAG` снимается с задачи (только если ревью реально
   дошло до вердикта — на инфраструктурных сбоях типа недоступного git тег
   остаётся, чтобы сверка подобрала задачу снова). В Slack и в лог уходит
   короткое сообщение об итоге: задача и куда она перемещена (или отдельное
   сообщение при `blocked`/внутренней ошибке сервиса — молчаливый отказ хуже
   ложного срабатывания).
8. Следующая задача берётся в работу по мере освобождения воркеров
   (`WORKER_CONCURRENCY`, по умолчанию 1 — строго по одной).

## Получение `CLAUDE_CODE_OAUTH_TOKEN`

Токен создаётся командой `claude setup-token`, выполненной **на машине с
браузером** (интерактивный OAuth-флоу):

```bash
claude setup-token
```

Полученное значение положите в `CLAUDE_CODE_OAUTH_TOKEN` в `.env`.

**Важно:** этот токен расходует квоту вашей подписки Claude Code (Pro/Max/
Team), как обычная интерактивная сессия. `ANTHROPIC_API_KEY` — это отдельный
способ авторизации, тарифицируемый по API отдельно от подписки. Задавать
**обе** переменные одновременно нельзя — сервис ожидает именно
`CLAUDE_CODE_OAUTH_TOKEN` и пробрасывает его в процесс `claude` через
окружение.

## Запуск

```bash
cp .env.example .env
# заполните .env: CLAUDE_CODE_OAUTH_TOKEN, CU_API_TOKEN, CU_TEAM_ID, CU_LIST_ID,
# SLACK_WEBHOOK_URL и т.д.

docker compose up -d --build
```

`GET /readyz` должен ответить 200, когда база открыта, репозиторий на месте
и `claude --version` отвечает.

## Регистрация вебхука

Вебхук создаётся отдельной командой (сервис при этом не запускает HTTP-сервер
и не обрабатывает задачи):

```bash
docker compose run --rm reviewer --register-webhook --webhook-url https://<ваш-хост>/webhook/clickup
```

Команда напечатает `CU_WEBHOOK_SECRET` — положите его в `.env` и перезапустите
сервис. Без этой переменной эндпоинт `/webhook/clickup` не поднимается, и
сервис работает только на сверке (`RECONCILE_INTERVAL`).

## Репозиторий внутри контейнера

Два варианта:

- **`REPO_URL` задан** — сервис клонирует репозиторий при старте. Для доступа
  по SSH смонтируйте deploy key как секрет (см. закомментированную строку в
  `docker-compose.yml`) — ключ должен иметь доступ только на чтение.
- **`REPO_URL` не задан** — смонтируйте свою рабочую копию с хоста томом в
  `REPO_PATH` (по умолчанию `/repo`).

**`REPO_PATH` не обязан быть одним git-репозиторием.** Он может быть общим
корнем с несколькими независимыми репозиториями как подпапками (раскладка
"монорепо из репозиториев", как в этом проекте: `panels/`, `sommerce/`,
`editor/` и т.д. рядом друг с другом). В этом случае:

- `.claude/commands/spec.md` и `.claude/commands/review.md` кладутся один раз
  в `REPO_PATH/.claude/commands/` — общие для всех репозиториев;
- `/spec` больше не пишет файл сама — она только выводит собранное ТЗ как
  текст ответа. Источник истины — таблица `run_stages` в БД (см. «Поэтапное
  выполнение и БД» ниже): Go сохраняет туда этот текст и сам записывает файл
  `REPO_PATH/specs/<ID задачи>.md`, которым пользуется `/review`, — **не**
  в `.claude/specs/`: Claude Code относит любой путь внутри `.claude/` к
  чувствительным и блокирует туда запись тулом Write независимо от
  `--allowedTools` (проверено эмпирически — ни широкое разрешение, ни
  точечный паттерн `Write(.claude/specs/**)` не помогают, permission_denials
  в JSON-ответе claude это подтверждает). Обычная директория `specs/` рядом
  с `.claude/` под это ограничение не подпадает. Файл перезаписывается из БД
  перед каждым запуском `/review`, в том числе при возобновлении прогона, —
  если рабочая копия свежая (например, после пересоздания контейнера) и
  файла ещё нет, он появится снова из уже собранного в БД содержимого без
  повторного дорогого вызова `/spec`;
- перед каждым ревью Go находит и обновляет (`git fetch --prune origin`) сам
  `REPO_PATH`, если он git-репозиторий, и/или все его прямые подпапки, в
  которых есть `.git` — какой из репозиториев реально относится к задаче,
  по-прежнему решает `/review`, а не Go;
- прогон падает только если не обновился **ни один** из найденных
  репозиториев — частичный сбой одного репо не останавливает проверку.

### SSH-доступ к репозиториям

Если репозитории используют SSH-remote'ы (`git@github.com:...`), контейнеру
нужен доступ к SSH-агенту хоста — приватные ключи в образ не копируются
и не должны копироваться. В `docker-compose.yml` это уже настроено через
проброс `$SSH_AUTH_SOCK` и монтирование `~/.ssh/config`/`~/.ssh/known_hosts`
(только для чтения). Требования:

- на хосте должен быть запущен ssh-agent с нужными ключами — проверить:
  `ssh-add -l`;
- запускать `docker compose up` из обычного терминала, где `SSH_AUTH_SOCK`
  уже экспортирован (на macOS это так по умолчанию);
- если `~/.ssh/config` использует Host-алиасы с `IdentitiesOnly yes` и
  конкретным `IdentityFile` (типичный случай для нескольких GitHub-аккаунтов)
  — такие алиасы работать не будут: приватный ключ доступен только через
  агент, а `IdentitiesOnly` запрещает его пробовать без файла на диске.
  Прогон это не останавливает (достаточно, что обновится хотя бы один
  репозиторий), но конкретно тот репозиторий не обновится;
- macOS-специфичные директивы `~/.ssh/config` (например, `UseKeychain` —
  форк OpenSSH от Apple) линуксовый ssh в контейнере не понимает; это уже
  обойдено через `GIT_SSH_COMMAND=ssh -o IgnoreUnknown=UseKeychain` в
  Dockerfile — сам файл `~/.ssh/config` при этом не редактируется.

### Notion-CLI

`/spec` и `/review` используют `notion-cli` для сбора ТЗ из Notion. Это не
публичный npm-пакет, а внутренний клиент приватного Notion API — рабочий
локальный checkout уже есть на хосте (`../cli/notion-private-api-mcp`
относительно `go_claude_agent/`, с уже установленными зависимостями и
сохранённой авторизацией). В контейнер он не копируется и не переустанавливается,
а монтируется как есть (`docker-compose.yml`):

- `../cli/notion-private-api-mcp:/opt/notion-cli:ro` — сам клиент;
- `~/.config/notion-cli` и `~/.cache/notion-cli` — конфиг с сохранённым токеном
  и кеш, тот же принцип, что и с SSH-агентом: используются реальные креды
  хоста, ничего не копируется в образ.

В образе (`Dockerfile`) лежит только тонкая обёртка `/usr/local/bin/notion-cli`,
делающая `node /opt/notion-cli/bin/notion-cli.js` доступным в `PATH`.
Проверить работоспособность: `docker compose exec reviewer notion-cli auth status`.

Кроме `/webhook/clickup`, `/healthz` и `/readyz`, сервис предоставляет:

### `POST /api/run` — ручной запуск проверки

```bash
# конкретная задача (те же условия — тег/статус/список/дедупликация — применяются как обычно)
curl -X POST localhost:8080/api/run -d '{"task_id":"abc123"}'

# конкретная задача с другой моделью/effort — только на этот прогон,
# текущее значение по умолчанию (см. /api/config/model) не меняется
curl -X POST localhost:8080/api/run -d '{"task_id":"abc123","model":"opus","effort":"high"}'

# без тела — немедленное пересканирование доски (та же логика, что у сверки)
curl -X POST localhost:8080/api/run
```

Отвечает `202` со списком ID задач, поставленных в очередь: `{"submitted":["abc123"]}`.
Постановка идёт через ту же функцию, что вебхук и сверка — ручной запуск не
обходит проверку тега/статуса/списка и дедупликацию. `model`/`effort`
осмысленны только вместе с `task_id` — для массового пересканирования
игнорируются.

### `GET /api/status` — что выполняется прямо сейчас

```bash
curl localhost:8080/api/status
```

Возвращает прогоны в состоянии `queued`/`running`: `{"active":[...],"count":1}`.

### `GET /api/stats?window=hour|day|all` — статистика и лог прогонов

```bash
curl localhost:8080/api/stats?window=day
```

Возвращает агрегаты за период (по умолчанию `all` — с момента первого
запуска) и сам лог прогонов с расходом токенов по каждой задаче:

```json
{
  "window": "day",
  "total_runs": 12,
  "by_status": {"done": 10, "failed": 2},
  "by_verdict": {"pass": 7, "fail": 3},
  "tokens": {"input_tokens": 145000, "output_tokens": 32000, "cost_usd": 1.84},
  "runs": [
    {"task_id": "abc123", "status": "done", "verdict": "pass",
     "session_id": "...", "input_tokens": 12000, "output_tokens": 2400,
     "cost_usd": 0.15, "started_at": "...", "finished_at": "..."}
  ]
}
```

Токены и стоимость берутся из `usage`/`total_cost_usd` JSON-вывода `claude -p`
и суммируются по обоим вызовам (`/spec` + `/review`) на задачу.

### `GET /api/config` — текущие настройки сервиса

```bash
curl localhost:8080/api/config
```

Настройки в читаемом виде (без токенов/секретов) — условие триггера,
переходы статусов, `ASSIGNEE_ON_FAIL`/`ASSIGNEE_ON_PASS` (с именем и
аватаром, если ID резолвится через ClickUp), модель/effort claude и т.д.
Используется дашбордом (см. ниже), но пригоден и для скриптов.

### `PUT /api/config/model` — сменить модель/effort claude по умолчанию

```bash
curl -X PUT localhost:8080/api/config/model -d '{"model":"haiku","effort":"low"}'
```

Меняет модель/effort для всех последующих вызовов `claude -p`, у которых
нет собственного переопределения (см. `POST /api/run` выше) — без
перезапуска сервиса: применяется сразу к работающему процессу и сохраняется
в БД (таблица `settings`), поэтому переживает и перезапуск. `effort` — одно
из `low`/`medium`/`high`/`xhigh`/`max` или пусто (использовать выбор claude
по умолчанию); `model` обязателен.

### `GET /api/queue` — текущая задача, буфер очереди и задачи без тега

```bash
curl localhost:8080/api/queue
```

Помимо активных и ожидающих задач (см. ниже), возвращает `other_to_check` —
остальные задачи в колонке `STATUS_TRIGGER`, у которых просто нет тега
`TRIGGER_TAG`: сверка их не подхватит сама, но дашборд позволяет запустить
проверку по ним вручную (см. `POST /api/run` выше).

Отдельно от `/api/status` (снимок из БД): здесь показано, что реально
выполняется прямо сейчас (`active`, с прогрессом по этапам и токенами в
реальном времени — см. «Поэтапное выполнение…» выше) и что лежит в
буфере в памяти, ожидая своей очереди воркера (`pending`) — это то, что
`/api/status` не видит, пока воркер не приступил к записи в БД.

### `POST /api/tasks/{task_id}/{cancel,pause,resume}` — управление текущей задачей

```bash
curl -X POST localhost:8080/api/tasks/abc123/cancel   # прервать прямо сейчас (жёстко — обрывает подпроцесс claude)
curl -X POST localhost:8080/api/tasks/abc123/pause    # остановить на границе этапов, дождаться "продолжить"
curl -X POST localhost:8080/api/tasks/abc123/resume   # продолжить прогон, остановленный паузой/обрывом процесса
```

`cancel`/`pause` отвечают `409`, если по этому `task_id` прямо сейчас ничего
не выполняется. `pause` не трогает статус/исполнителей карточки и не ставит
на паузу всю очередь (в отличие от паузы при исчерпанном лимите использования,
см. ниже) — только этот прогон, до явного `resume`.

### `GET /api/runs/{id}` — детали одного прогона

```bash
curl localhost:8080/api/runs/42
```

Сам прогон, этапы (`run_stages`) и полный лог вызовов claude с токенами
каждого (`claude_invocations`) — см. «Поэтапное выполнение…» выше.

### `GET /api/invocations?window=hour|day|all` — токены по сессиям

```bash
curl localhost:8080/api/invocations?window=day
```

Плоский лог вызовов claude (сессий `/spec` и `/review`) по всем прогонам за
период, с токенами/стоимостью каждого вызова и суммой по периоду —
детализация на уровень ниже, чем `/api/stats` (там — суммарно на прогон).

## Веб-дашборд

`GET /` — одностраничный дашборд (светлая/тёмная тема, переключатель в
правом верхнем углу): текущие настройки (включая смену модели/effort по
умолчанию прямо со страницы), текущая задача с кнопками прервать/пауза/
продолжить, очередь (плюс, под чертой, остальные задачи в колонке-триггере
без тега — их тоже можно запустить вручную, при желании с другой моделью/
effort только на этот прогон), статистика за час/день/всё время и токены по
сессиям. Работает целиком через перечисленные выше JSON-эндпоинты
(опрашивает `/api/queue` каждые 5 секунд, остальное — раз в минуту или по
клику) — отдельного бэкенда не требует.

## Graceful shutdown и восстановление после обрыва

Сервис старается не обрывать прогон ревью посреди работы:

- по `SIGTERM`/`SIGINT` перестаёт принимать новые вебхуки и сверку, но
  **дожидается завершения уже идущих прогонов** (до `REVIEW_TIMEOUT`, по
  умолчанию 15 минут) — обычный `docker compose up -d`/пересборка не обрывает
  активную проверку;
- `docker-compose.yml` задаёт `stop_grace_period: 16m` — по умолчанию Docker
  ждёт остановки контейнера всего 10 секунд и потом жёстко убивает процесс
  (`SIGKILL`); без этого поля graceful shutdown не успевал бы отработать.
  Если увеличиваете `REVIEW_TIMEOUT` — увеличьте и `stop_grace_period` с запасом.

Если прогон всё же прервался (упал хост, `docker compose kill`, нехватка
памяти и т.п.) — при следующем старте сервис не просто помечает прогон
`failed`, а **сам доводит его до конца**: находит все задачи, застрявшие в
статусе `running`, и заново прогоняет именно их (`git fetch` → `/spec` →
`/review` → перевод в нужную колонку → комментарий), не дожидаясь, пока
сверка случайно найдёт их снова. Это отдельный путь постановки в очередь
(`Queue.SubmitResume`), который **не проверяет условие триггера** (тег/
статус/список) — раз ревью уже было начато для этой задачи, оно доводится
до конца независимо от того, как сейчас выглядит её карточка (например, она
может застрять в `STATUS_RUNNING` без тега).

## Пауза при исчерпанном лимите использования claude

Если `claude -p` сообщает об исчерпанном лимите использования (usage limit/
rate limit подписки или API) — это не результат ревью и не сбой процесса,
а временное состояние аккаунта. Сервис отличает такой случай от обычной
ошибки (см. предыдущий раздел) и обрабатывает его иначе:

- карточка задачи возвращается в исходное состояние — статус обратно на
  `STATUS_TRIGGER`, снятый на время проверки исполнитель восстановлен, тег
  триггера не трогается — то есть заново попадает под условие взятия в
  работу;
- прогон в БД помечается `paused` (не `failed`) — это тоже не блокирует
  повторную постановку;
- **вся очередь** ставится на паузу минимум на `USAGE_LIMIT_PAUSE` (по
  умолчанию 30 минут) — на это время `processTask` пропускает любые задачи,
  не трогая ClickUp и не создавая запись в БД, чтобы не долбить claude
  тем же лимитом снова и снова;
- по окончании паузы её обычная сверка (`RECONCILE_INTERVAL`) сама находит
  и заново ставит задачу в очередь — отдельный таймер для этого не нужен;
- в Slack уходит отдельное уведомление ⏸️ (не путать с ⛔ blocked или
  🔥 внутренней ошибкой сервиса).

Определяется по тексту ответа claude (устойчивого структурированного кода
ошибки специально под этот случай `claude -p --output-format json` не даёт),
поэтому детектор (`review.ErrUsageLimit`) намеренно консервативный — по
ключевым фразам вроде "usage limit"/"rate limit"/"usage credit" в тексте
ответа или stderr процесса.

## Подключение к базе данных

Состояние (таблицы `runs`, `run_stages` и `claude_invocations`, см. раздел
«Поэтапное выполнение, ТЗ и лог токенов в БД» ниже) хранится в
SQLite-файле `DB_PATH` (по умолчанию `/data/state.db`). Том `/data`
смонтирован с хоста в `./data` (`docker-compose.yml`) — файл лежит прямо
в `go_claude_agent/data/state.db` и открывается напрямую, без остановки
контейнера:

```bash
sqlite3 ./data/state.db          # локальный sqlite3 (есть на macOS из коробки)
sqlite3 ./data/state.db ".tables"
sqlite3 -header -column ./data/state.db "SELECT * FROM runs ORDER BY id DESC LIMIT 10;"
```

GUI-клиенты (DB Browser for SQLite, TablePlus и т.п.) подключаются к тому же
пути как к обычному SQLite-файлу. Внутри контейнера тот же файл доступен
через `sqlite3` (пакет есть в образе): `docker compose exec reviewer sqlite3 /data/state.db`.

**До этого изменения** (или если у вас старый том `reviewer-data`) файл лежал
в именованном Docker-томе, который на macOS Docker Desktop живёт внутри
Linux-VM и не виден напрямую с хоста — тогда единственный способ дотянуться
до файла: `docker compose exec reviewer cat /data/state.db > /tmp/state.db`
(обычный `docker cp`/`docker compose cp` может падать на этом хосте из-за
пробрасываемого сокета SSH-агента — `cat` через `exec` работает всегда).

## Поэтапное выполнение, ТЗ и лог токенов в БД

Один прогон ревью (`runs`) выполняется семью этапами подряд: `setup` →
`commands_check` → `git_fetch` → `spec` → `review` → `decide` → `comment`.
Каждый этап логируется в таблицу `run_stages` — отдельная строка на
`(run_id, stage)` со статусом (`running`/`done`/`failed`) и JSON-данными,
нужными, чтобы не повторять этап при возобновлении:

```bash
sqlite3 -header -column ./data/state.db \
  "SELECT stage, status, started_at, finished_at FROM run_stages WHERE run_id = 42 ORDER BY id;"
```

Если прогон прервался (падение процесса — см. «Graceful shutdown и
восстановление» — или пауза на лимите использования, см. предыдущий раздел),
`Store.ReopenOrEnqueue` при повторной постановке той же задачи находит
именно этот `run_id` и продолжает его: этапы, уже отмеченные `done`, не
выполняются заново — их результат берётся из `run_stages.data`. Это
особенно важно для этапа `spec`: это дорогой вызов claude, и второй раз
дёргать его без необходимости — прямой перерасход токенов.

**Собранное ТЗ хранится в БД, а не только в файле.** `/spec` больше не
сохраняет файл сама (см. «Репозиторий внутри контейнера» выше) — она лишь
выводит собранный документ как текст ответа, и именно этот текст Go
сохраняет в `run_stages.data` этапа `spec` (поле `content`). Файл
`specs/<ID>.md`, который читает `/review`, Go перезаписывает из этого поля
каждый раз перед запуском `/review` — в том числе при возобновлении,
если рабочая копия успела обновиться и файла в ней ещё нет. Таким образом
именно БД, а не файл на диске, является источником истины для содержимого
ТЗ, используемого проверкой.

**Полный лог вызовов claude — в `claude_invocations`.** Отдельно от
`run_stages` (там хранится только то, что нужно для возобновления), каждый
реальный вызов `claude -p` (что для `/spec`, что для `/review`) добавляет
свою строку сюда: полный текст запроса и полного ответа, модель и уровень
усилий, с которыми он выполнялся, и токены/стоимость именно этого вызова.
`id` растёт монотонно, поэтому порядок строк по `run_id` — это и есть
хронология сессий claude в рамках одного прогона:

```bash
sqlite3 -header -column ./data/state.db \
  "SELECT id, stage, session_id, model, effort, input_tokens, output_tokens, cost_usd, started_at
   FROM claude_invocations WHERE run_id = 42 ORDER BY id;"

# полный текст последнего ответа claude по конкретному прогону и этапу
sqlite3 ./data/state.db \
  "SELECT output FROM claude_invocations WHERE run_id = 42 AND stage = 'review' ORDER BY id DESC LIMIT 1;"
```

Тот же полный ответ (текст + токены + `session_id` + `subtype`/`is_error`)
уходит и в структурированный лог сервиса (`docker compose logs -f reviewer`,
JSON-строки с `"msg":"claude response"`) — длинный ответ в логе обрезается
(~8000 символов), полный текст без обрезки всегда доступен в БД.

**Расход токенов виден в реальном времени, а не только по завершении этапа.**
`claude -p` запускается в потоковом режиме (`--output-format stream-json`);
по ходу выполнения (не чаще раза в 2 секунды) Go обновляет `runs.input_tokens`/
`output_tokens` уже потраченными на текущий момент значениями — не дожидаясь
конца `/spec` или `/review`. Если подозреваете перерасход — можно смотреть
на растущие цифры прямо во время прогона:

```bash
watch -n2 'sqlite3 -header -column ./data/state.db \
  "SELECT id, task_id, status, input_tokens, output_tokens, cost_usd FROM runs WHERE status = '"'"'running'"'"';"'
```

Точная стоимость (`cost_usd`) в промежуточных обновлениях не считается
(API отдаёт её только по завершении вызова) — финальные, уже точные цифры
записываются при переходе прогона в `done`/`failed`/`paused`.

## Модель и уровень усилий claude

`CLAUDE_MODEL`/`CLAUDE_EFFORT` (флаги `--model`/`--effort` каждого вызова
`claude -p`) задаются в `.env` — это значение по умолчанию при самом первом
запуске сервиса. По умолчанию в коде — `sonnet`/`high`; сейчас в `.env`
временно выставлены `haiku`/`low` — самая дешёвая и быстрая пара, чтобы
обкатать функционал этого раздела без расхода токенов на дорогой модели.
Вернуть на `sonnet`/`high`, когда обкатка закончена.

Модель/effort по умолчанию можно поменять и не трогая `.env` — через
дашборд (см. «Веб-дашборд» выше) или `PUT /api/config/model` — изменение
применяется сразу же, без перезапуска, и сохраняется в БД (таблица
`settings`): при следующем перезапуске сервис берёт значение оттуда, а не
заново из `.env`. Отдельно, для одной конкретной задачи, модель/effort
можно переопределить только на этот прогон через `POST /api/run` или кнопку
запуска в дашборде — общий дефолт при этом не меняется.

## Границы ответственности

Сервис **не делает**: не разбирает требования, не ищет ветку, не читает ТЗ и
не анализирует комментарии задачи (это делают `/spec` и `/review`), не
встраивает промпты в Go-код, не использует Claude API напрямую, не удаляет
комментарии, не имеет веб-интерфейса, метрик Prometheus или авторизации —
это вне объёма задачи.

**Особый случай — исполнители.** В отличие от исходного ТЗ, этот сервис
временно снимает всех исполнителей на время проверки и переназначает задачу
по итогу (человеку-ревьюеру при успехе, разработчику/автору при провале —
см. приоритет в разделе «Как это работает», п. 6) — это осознанное решение
владельца проекта под конкретный workflow ClickUp-доски, а не общее правило
"никогда не трогай исполнителей".
