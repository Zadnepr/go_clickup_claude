# reviewer

Go-микросервис автоматического ревью задач ClickUp: следит за доской,
запускает код-ревью силами `claude -p` и возвращает результат в задачу
ClickUp и в Slack.

Сервис — сантехника. Он не анализирует код, не читает ТЗ и не формулирует
замечания: вся содержательная работа выполняется командами `/spec` и
`/review` внутри `claude -p`, которые живут в целевом репозитории
(`.claude/commands/`) и меняются без пересборки образа.

## Как это работает

1. ClickUp присылает вебхук (или сервис сам сверяется раз в
   `RECONCILE_INTERVAL`) — событие ведёт к проверке карточки задачи.
2. Если у задачи есть тег `TRIGGER_TAG`, она в колонке `STATUS_TRIGGER` и по
   ней ещё нет активного прогона — задача берётся в работу.
3. Задача переводится в `STATUS_RUNNING`, репозиторий обновляется
   (`git fetch --prune origin`), запускаются две отдельные сессии
   `claude -p`: сперва `/spec`, затем `/review`.
4. `/review` печатает полный текст ревью и обязан завершить вывод строкой
   `ИТОГ: критичных=N важных=N минор=N статус=pass|fail|blocked` — см.
   [review-patch.md](review-patch.md) для патча, добавляющего это требование
   в вашу команду `/review`.
5. По вердикту задача переводится в `STATUS_PASS` или `STATUS_FAIL`,
   назначается исполнитель, публикуется комментарий с текстом ревью, в Slack
   уходит уведомление.

## Получение `CLAUDE_CODE_OAUTH_TOKEN`

Токен создаётся командой `claude setup-token`, выполненной **на машине с
браузером** (интерактивный OAuth-флоу):

```bash
claude setup-token
```

Полученное значение положите в `CLAUDE_CODE_OAUTH_TOKEN` в `.env`.

**Важно:** этот токен расходует квоту вашей подписки Claude Code (Pro/Max/
Team), как обычная интерактивная сессия. `ANTHROPIC_API_KEY` — это отдельный
способ авторизации, тарифицируемый по API отдельно от подписки. Задавать
**обе** переменные одновременно нельзя — сервис ожидает именно
`CLAUDE_CODE_OAUTH_TOKEN` и пробрасывает его в процесс `claude` через
окружение.

## Запуск

```bash
cp .env.example .env
# заполните .env: CLAUDE_CODE_OAUTH_TOKEN, CU_API_TOKEN, CU_TEAM_ID, CU_LIST_ID,
# SLACK_WEBHOOK_URL и т.д.

docker compose up -d --build
```

`GET /readyz` должен ответить 200, когда база открыта, репозиторий на месте
и `claude --version` отвечает.

## Регистрация вебхука

Вебхук создаётся отдельной командой (сервис при этом не запускает HTTP-сервер
и не обрабатывает задачи):

```bash
docker compose run --rm reviewer --register-webhook --webhook-url https://<ваш-хост>/webhook/clickup
```

Команда напечатает `CU_WEBHOOK_SECRET` — положите его в `.env` и перезапустите
сервис. Без этой переменной эндпоинт `/webhook/clickup` не поднимается, и
сервис работает только на сверке (`RECONCILE_INTERVAL`).

## Репозиторий внутри контейнера

Два варианта:

- **`REPO_URL` задан** — сервис клонирует репозиторий при старте. Для доступа
  по SSH смонтируйте deploy key как секрет (см. закомментированную строку в
  `docker-compose.yml`) — ключ должен иметь доступ только на чтение.
- **`REPO_URL` не задан** — смонтируйте свою рабочую копию с хоста томом в
  `REPO_PATH` (по умолчанию `/repo`).

## Переменные окружения

Полный список — в [.env.example](.env.example) и в исходном ТЗ
([build-reviewer-service.md](build-reviewer-service.md)). Значения статусов и
тегов сравниваются без учёта регистра и лишних пробелов.

## Структура проекта

```
cmd/reviewer/main.go   точка входа, --register-webhook, сверка, graceful shutdown
internal/config        загрузка и валидация окружения
internal/clickup        клиент API: задача, статус, исполнители, комментарий, вебхук
internal/slack          отправка уведомлений (Block Kit)
internal/store          SQLite, таблица runs (дедупликация, восстановление)
internal/review         запуск claude, разбор вывода, контракт вердикта
internal/queue          очередь и воркеры, оркестрация полного цикла задачи
internal/httpapi        вебхук, healthz, readyz
review-patch.md         патч контракта вердикта для команды /review
```

## Тесты

```bash
go test ./...
```

Клиент ClickUp тестируется против `httptest.Server`, реальные вызовы к
ClickUp/Slack/`claude` в тестах не выполняются.

## Границы ответственности

Сервис **не делает**: не разбирает требования, не ищет ветку, не читает ТЗ и
не анализирует комментарии задачи (это делают `/spec` и `/review`), не
встраивает промпты в Go-код, не использует Claude API напрямую, не снимает
исполнителей и не удаляет комментарии, не имеет веб-интерфейса, метрик
Prometheus или авторизации — это вне объёма задачи.
